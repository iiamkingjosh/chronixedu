## A second contention flake, same day: `cronLock.db.test.ts` could deadlock itself

Surfaced by the first full DB run after the seed fix, and a second instance of
doctrine 15 in one day. The test started `first`, **slept 100ms**, and assumed `first` held
the advisory lock by then. Under load it did not: `second` won the race, took the lock,
ran the job and parked on `gate` — but `release()` was only called after `second`
returned, so each waited on the other. 30s test timeout; then `afterAll(pool.end)` hung on
the still-checked-out client, and Jest could not exit.

The state was readable directly: `pg_locks` showed one advisory lock held by a backend
idle for over an hour, whose last statement was `pg_try_advisory_lock` — and the run
logged exactly one `cron_skipped_lock_held` where the test's design implies two
`runExclusive` attempts against a held lock. `runExclusive` itself is correct (it pins one
client for lock and unlock); the defect was a sleep standing in for a synchronisation.

Reproduced with the sleep cut to 0ms: 1 of 6 runs hit the identical
test-timeout-then-hook-timeout signature. Fixed by resolving a promise from *inside* the
job — `runExclusive` only runs the job after acquiring the lock, so awaiting it proves
`first` holds the lock before `second` is tried, on any machine — and by releasing the gate
in a `finally` so a failed assertion cannot strand the lock. Six clean runs of the fix are
reported but are not the evidence; the evidence is that no timing assumption remains.

Tooling note: stopping the backgrounded run killed the shell wrapper but left `node`
alive on Windows, which is how a connection held the lock for an hour after the run
"ended". Check for orphaned `jest` processes before reading lock state.

## Three integration "passes" that tested nothing (found 28 Sep 2026)

`apps/api/tests/resultEngine.test.ts` guarded each test with `if (skip) return;`, setting
`skip` when a student called Fatima had no Mathematics scores in the target database. Jest
reports an early return as PASSED. The integration `globalSetup` — introduced in `d24dc48`
on 17 June, the same commit that last touched this file — seeds Fatima's user and student
rows but never her scores, so on every clean database, which is every CI run, all three
tests returned immediately and counted as passes. The last integration run reported 194
passed; the honest figure was 191 passed and 5 skipped. Same shape as the analytics
counts: a real number that measures something other than what it names.

It was worse than idle. Two of the three upserted with
`ON CONFLICT (student_id, term_id, component_id)`, and migration 028 (`2c5dd1d`, 17 Sep)
replaced that constraint with one including `subject_id`. Run against the current schema,
the clause raises `there is no unique or exclusion constraint matching the ON CONFLICT
specification` — measured. So for the last eleven days the skip was hiding a test that
would have failed, not just one that did not run.

The coverage it claimed was not held anywhere else. `computeStudentSubjectResult` had no
other test. `classSummary.db.test.ts` has a ranking test, but it enters no scores, so every
student averages 0 and ties at position 1: its tie branch executes only in that
degenerate case and never checks the 1, 1, 3 gap.

Fixed by porting to `src/__db_tests__/resultEngine.db.test.ts` against `seed()`, with every
assertion unconditional and the tie constructed rather than hoped for. Verified by
mutation, one at a time: switching the engine to dense ranking fails exactly the
`[85, 85, 72, 65] → [1, 1, 3, 4]` test; replacing the weighted contribution with the raw
score fails exactly the weighting test. The second is the telling one — the seed's
components have max_score equal to weight (30/30, 70/70), so the weighting is an identity
and **nothing else in the suite would catch a raw-score bug**. The test raises CA1's max
to 40 so the formula has to run. The dead file is deleted.

## The same defect one layer shallower, and a fixture that could not be wrong (28 Sep 2026)

### `studentsBulkImport`: five passes in CI that never ran

Found on review, in the file the `resultEngine` fix had cited as the model. Its five
commit tests probed Supabase Auth in `beforeAll` and did `console.warn` + `return` when it
was unusable — a stated reason, which was the improvement, but `return` is still a PASS.
`console.warn` tells a human reading the output; only `it.skip` tells the runner, which is
what produces the number.

It was worse in CI than locally: `ci.yml` sets `SUPABASE_URL` to `127.0.0.1:54321` with a
placeholder key and runs **no** Supabase service, so Auth has never been available there
and those five have passed on every CI run without executing. With `resultEngine`'s three,
CI's integration count carried **eight** phantom passes.

A skip must be decided at collection time, before any `beforeAll` runs — so the suggested
"probe in `beforeAll`, then `describe.skip`" cannot work as stated. The probe now lives in
`jest.globalSetup.ts`, which completes before any file is collected, and reaches the test
files through `process.env.TEST_AUTH_UNAVAILABLE`; the five use `itWithAuth = … ? it.skip :
it`. The one test in that block that needs no Auth (a 403 check) still runs. Verified both
ways: Auth down → `5 skipped, 7 passed`; Auth up → `12 passed`. The probe retries three
times: a single `fetch failed` against a healthy local stack skipped five runnable tests
once, and a skip should mean Auth is down, not that one connection dropped.

**Open, pre-existing:** `reuses an existing parent … for two siblings in the same file`
fails intermittently with `created: 1` where 2 is expected — reproduced on code predating
this change (1 in ~8). Rows commit sequentially, so it is not a race within the batch. The
likely cause is a transient Auth failure on the second sibling's account, which would be
correctly reported as a failed row, but that is unconfirmed: the test asserted only the
count. It now asserts the failed rows *with their reasons* first, so the next occurrence
names its own cause.

| Mutation | Tests catching it before | After |

### Connection timeouts: three wrong attributions, then the host

The first full run after these changes had `timeout exceeded when trying to connect`, and
it recurred intermittently. It took four measurements to place, and three explanations were
withdrawn on evidence along the way — recorded because each looked right at the time:

1. *Docker port forwarding.* Refuted: 5,151 raw TCP connects **during** a suite run, none
   failed, max 123ms. (A first measurement taken at rest proved nothing — doctrine 15.)
2. *`TRUNCATE` flushing to disk.* Real — a watcher caught `IO:DataFileImmediateSync` at up
   to 6.9s per TRUNCATE in both old and new code — but refuted as the cause: with
   `fsync=off` Postgres had no wait over one second and the timeouts still occurred.
3. *This batch.* 3 of 7 runs against 0 of 2 looked like a lean; it was noise.

Final: the host was paging — 15.4 GB RAM, 1.6 GB free, 36 GB committed — so the jest
process stalled long enough for `pg-pool`'s own 10s timer to fire while Postgres sat idle.
The same stalls account for two native `0xC0000409` crashes of the jest process and the
earlier `ECONNRESET`. Not a code defect; guidance added to CLAUDE.md.

What survived as a real improvement is (2): with durability off the suite runs in **99s
instead of 225–242s**, and a 7s TRUNCATE no longer eats a third of the seed's 20s
`statement_timeout`. CI now applies it via `ALTER SYSTEM` in a step that fails if `fsync`
is still on; local instructions are in CLAUDE.md.

## M-money — corrected and fixed (26 Sep 2026)

The finding was recorded as accumulation drift: repeated partial payments leaving a
residue so an invoice never settles. **Measured, that does not happen.** Every money
column is `numeric(12,2)` and pg returns exact 2-dp strings, so the single float
addition per payment is laundered by the round-trip. A search over totals from ₦1,000 to
₦500,000 split 3, 6, 7 and 9 ways found **zero** cases where the sum missed the total,
and a DB test replaying three instalments passes against the old code.

The real defect was one line away and worse, because it **rejects** a payment rather
than mis-stating one. The overpayment guard compared a float *subtraction* against the
amount tendered:

```
250000.00 − 83333.33 = 166666.66999999998
parent tenders the exact remaining 166666.67
166666.67 > 166666.66999999998  →  OverpaymentError
```

Three of six realistic settlement cases were refused at the counter. Fixed by doing the
comparison and the balance in integer kobo (`toKobo`/`fromKobo`), formatted once on the
way into `numeric(12,2)`. `toKobo` rounds `(n*100).toFixed(6)` rather than `n*100`,
because `1.005 * 100` is `100.49999999999999` and the route's
`amount: z.number().positive()` constrains no decimal places.

### Follow-up, same day: kobo at the boundary, not just in the arithmetic

Three residuals closed while the file was open.

1. **`toKobo` rounded a third decimal instead of rejecting it.** `amount: z.number().positive()`
   constrained no decimal places, so ₦1.005 was accepted and silently recorded as ₦1.01 —
   no error, no log, and a receipt that disagrees with the cash drawer. Rounding fixed the
   arithmetic and left unanswered whose kobo it was. Routes now parse a decimal **string**
   via `nairaToKobo`, which rejects a third decimal place outright.
2. **The single-payment path now matches the bulk path.** Bulk import already took
   `amount: z.string()`; the single route took `z.number()`. The browser's form field is
   text and the old client did `Number(amount)` before sending, discarding the exact value
   it held. Both sides now pass the string, so no float exists on either side of the wire.
   The Paystack initiate route was converted too — its `Math.round(payAmount * 100)` carried
   the same half-kobo subtlety.
3. **Paystack's kobo stays kobo.** `verifyPaystackTransaction` returned
   `json.data.amount / 100`, turning an exact integer into a naira float that something
   downstream multiplied back. It round-tripped correctly only because of the `toFixed(6)`
   guard in `toKobo` — added for an unrelated reason, and load-bearing here without
   anything saying so. `PaystackVerification.amountKobo` now passes the integer through.

`toKobo`/`fromKobo` moved to `services/money.ts`. They had been in `db/queries/fees`, and
route tests that `jest.mock('../db/queries/fees')` were auto-mocking these pure functions
to `undefined` — a route read a balance as `NaN` and the test reported a confusing diff
rather than the cause. A helper a route calls has no business behind a mock boundary meant
for queries.

Worth carrying forward: the per-payment path was safe **by accident**, not by design —
the column type corrected the error on every write. A future loop that accumulates
without a round-trip, or a column changed to `double precision`, removes that
protection silently.

## Platform billing counts current enrolment (30 Sep 2026)

Migration 044 (`b39f1cf`, the second reader's) made `platform_subscriptions.amount_naira` a
derived value — a per-student rate × the school's student count — instead of a number a
super-admin typed. Right, and its count was wrong: `COUNT(*) FROM students`, which is every
student ever enrolled at the school and can only grow (no status column, no student DELETE
outside the wipe, no graduation concept). Migration 045 defines a **billable** student as one
with a `student_classes` row in the school's **current** academic session, counted once, and
moves the recompute triggers to enrolment and session rollover. Full reasoning, including
the no-current-session decision, in the migration header and CLAUDE.md, "Platform billing".

Two things found on the way, one fixed and one not:

- **Two suites were failing from `b39f1cf`, and CI did not report it.** 044 made every paid-subscription write raise until a rate exists, and two suites wrote paid subscriptions with literal amounts: `partnerRevenue.db.test.ts` (10 failures) and `tests/superAdmin.test.ts` (9), both seen in local runs. It had not, and CI was not read at any point in that work: it has been red on every commit for a different reason (next entry) and never reached the test jobs.
- **`student_classes` has no unique constraint on `(student_id, session_id)`** — only
  plain indexes (migration 001). Nothing stops two rows for one student in one session,
  which is why billing counts DISTINCT. Left as is: adding the constraint means deciding
  what a mid-session class move should do to the old row, which is a product question,
  not a billing one. **Open.**

Sixteen tests in `platformBilling.db.test.ts`; 15 of the 16 fail with migration 045 removed and the
route change stashed, verified by doing exactly that rather than by inspection.

## C-4 plan (drafted 26 Sep 2026; not yet executed)

C-4 is the last Critical still **Documented** rather than Fixed. The API connects as the
table owner, which is why the audit guards in migrations 036-039 are accident-proofing
rather than enforcement, why `DISABLE TRIGGER ALL` is available to the application, and
why RLS is inert across every route. Split in two, because the halves have very
different risk profiles.

### Measured first (probes run against production, roles dropped afterwards)

| Question | Answer |
|---|---|
| Can a non-owner role authenticate through the Supavisor pooler? | **Yes** — `<role>.<project-ref>` as username. `current_user` came back as the probe role. |
| Do privileges enforce through it? | **Yes** — `SELECT` on an ungranted table returned `permission denied for table users`. |
| Does RLS activate for a non-owner? | **Yes, immediately.** `SELECT count(*) FROM schools` returned **0 rows**. Originally attributed to "no policy admits the role" — that was the wrong cause. The policy admits it; its predicate evaluates to NULL. See the row below. C-4a does not merely fail to deliver RLS, it switches RLS on for all 44 tables at once. |
| Do the existing policies work once RLS applies? | **No — all 42 tenant policies are inert.** They are keyed on `auth.jwt() ->> 'school_id'`, which reads `request.jwt.claims`, set by PostgREST and GoTrue. This API signs its own HS256 tokens and uses Supabase Auth only as a password verifier, so a direct `pg` connection never populates that setting. Measured from the pool: `auth.jwt()` is NULL, and `WHERE school_id = ((auth.jwt()->>'school_id'))::uuid` matched **0 of 2** real `payments` rows. Of 81 policies: 42 use `auth.jwt()`, **0 use `current_setting`**, 36 are service-role bypass. |
| Is `BYPASSRLS` grantable? | **Yes** on 17.6 — `postgres` is non-superuser but holds `CREATEROLE` and the attribute itself (PG16 relaxed the superuser requirement). **Not used** — see below. |
| Does any data access bypass `pg`? | **No.** 35 service-role call sites: `auth.admin` 18, `storage` 16, `auth.getUser` 1, and **zero** PostgREST `.from()` table access. The privilege boundary is the whole data path. |
| Which tables are read-only to the API? | Effectively none — **42 of 44 are written**. A per-table read/write split is a gesture; the real boundary is operation-level. |

### Two readers, for the claims that decide something

Most of the corrections during this work came from reading production through two
independent paths — one party reporting, the other querying — and the mismatch was the
finding. The 16:02 timestamp that was never measured; the "263 unprocessed" rows that
were not a queue; 039 being live 90 minutes before it was reported unapplied; the 29
principal-less schools that showed 038 had guarded the wrong operation. **In every case
the error was in the reading, not in the database.** One reader who both queries and
reports produces a mistaken query, a mistaken report and a mistaken confirmation
together, with nothing to disagree with.

Agent access to Railway and Supabase does not change that; it makes collapsing the two
steps easier. Use direct access freely for routine checks, and keep the second read for
claims that decide something.

**Specifically for step 5 below.** When `APP_DATABASE_URL` switches, the failure is
`permission denied` on a route nobody exercised — and whoever wrote the grants is the
worst-placed person to notice which route was missing from their own inventory. Hand
over the grant set and the route inventory as artifacts and have them checked against
each other, not against a description of them.

### C-4a — privilege hardening

Because RLS activates the moment the app stops being owner, the cutover needs every
table to stay readable until C-4b replaces the policies properly. Use a **named
permissive policy per table**, not `BYPASSRLS`: the attribute concentrates the whole
risk into the single instant it is dropped, and the failure shape there is a silent
empty result. Per-table policies give an enumerable backlog
(`SELECT tablename FROM pg_policies WHERE policyname LIKE 'app_bypass_%'`), a per-table
cutover, and no dependence on the `BYPASSRLS` answer.

1. Create the app role; confirm it authenticates through the pooler.
2. `GRANT` broadly, then **`REVOKE` by operation**: no `TRUNCATE` on any table, no
   `DELETE`/`UPDATE` on `audit_logs`.
   **Corrected 28 Sep 2026, before execution:** read literally, "no UPDATE on
   `audit_logs`" is migration 036 again one layer down — the notification worker updates
   `processed_at`. The proposed grant revokes UPDATE and re-grants `UPDATE (processed_at)`.
   And only DML is granted, not `ALL`, so TRUNCATE is absent by construction rather than
   revoked. Artifacts for the second read: `docs/c4a/` (start with its README).
   **Prove each denial by attempting it as the role, BEFORE writing any `REVOKE`.** A
   `REVOKE` written first and tested afterwards invites keeping a no-op because it reads
   well; probing first means the migration contains only revocations that revoke
   something. A revoke standing in for a check nobody ran is exactly the defect pattern
   this audit kept finding.

   **Probe with the grant set you intend to ship, not a bare role.** A fresh role denies
   almost everything, so it would report the prohibitions as free when they are not.
   `CREATE TABLE` depends on schema-level `CREATE` on `public`; `TRUNCATE` depends on
   table-level grants. Apply the intended `GRANT USAGE ON SCHEMA public` +
   `GRANT ALL ON ALL TABLES IN SCHEMA public` first, then attempt both. Expect
   `CREATE TABLE` to be denied already (PG15+ no longer grants `CREATE` to `PUBLIC`, and
   `USAGE` is not `CREATE`) and `TRUNCATE` to be permitted (`ALL` includes it) — so the
   DDL revoke is likely a no-op and the TRUNCATE revoke is likely real. Which is which
   must be measured on the shipping grant set, not assumed from this paragraph.
3. `app_bypass_<table>` permissive policy (`USING (true) WITH CHECK (true)`) per table,
   plus a test asserting every public table has exactly one. The test is the inventory.
4. `ALTER DEFAULT PRIVILEGES` for the app role, or the next migration's table is born
   outside the boundary and the deploy after it fails with `permission denied`.
5. **Three named connection strings**, not one overloaded variable:
   `DATABASE_URL` (owner, migrations only — the pre-deploy gate reads it),
   `APP_DATABASE_URL` (app role, the pool), `AUTH_DATABASE_URL` (the unpooled login
   client, H-7's leftover). `client.ts` refuses to start without `APP_DATABASE_URL`
   rather than falling back. A service that migrates fine and serves nothing, or that
   authenticates everything except logins, is the slowest failure to diagnose.
   **Stage the rollback before switching.** The realistic failure is `permission denied`
   on a route nobody exercised, found in production. Keep the owner URL in place and
   documented as the revert, and remove owner access from nothing until a full pass over
   the app has run against the new role. The revert being a variable change rather than a
   redeploy is worth arranging deliberately.
6. `withTenant()` lands here, while every table is still permissive — so the wrapper is
   in place and enforced before it becomes load-bearing.

### C-4b — RLS as real enforcement

**Not 44 removals — 44 removals plus a rewrite of everything migration 031 added.**
"The real policies already exist and merely need the bypass removed" was doing real work
in the estimate and it is false: every 031-era tenant policy is keyed on `auth.jwt()`,
which this app never populates, so all 42 are inert and must be rewritten to
`current_setting('app.school_id', true)` as part of the same work. Size the window
accordingly.

The one consolation is the failure direction. NULL comparison filters rows, so an
un-rewritten policy returns zero rows rather than another tenant's — fail-closed and
loud, which is the property the policy design wanted anyway, arriving by accident.

Each table is still independently verifiable: "replace `app_bypass_scores` with a real
policy" remains the unit of work, it is simply a rewrite rather than a deletion.

**C-4b also removes a vendor dependency, not only the inert policies.** The 42 tenant
policies call Supabase's `auth.uid()` / `auth.jwt()`. C-4a's correctness then depends on those
bodies never naming schema `auth` (inlining would fail at planning, for every query under the
policy) and never raising on an absent setting — properties of SQL this project does not
control (`docs/c4a/README.md`, "The platform dependency"). Rewriting the policies to
`current_setting('app.school_id', true)` puts the setting and its missing_ok flag in our own
hands.

**Pilot the rewrite on `notices_tenant`.** Of the tenant policies that need converting,
it is the cleanest: `school_id = (auth.jwt() ->> 'school_id')::uuid` reads `school_id`
off the row directly, with no join to reason about, so the change is pure substitution —
`auth.jwt()` → `current_setting('app.school_id', true)` and nothing else. That isolates
the one variable C-4b is actually testing from every other thing that could go wrong in
a policy (a join through `students`, a per-user `auth.uid()` term, a compound predicate).
Its blast radius is small too: `notices` has exactly one reader
(`GET /:schoolId/student/notices`) and one writer (`routes/notices.ts`), both
owner-connected, so a wrong predicate shows up in a single DB test rather than across
the product. Do it first, confirm the session variable behaves under `withTenant()`,
and only then start on the ones with joins.

**The policy set to rewrite is 80, not 81, and it is now pinned.** Reconciled on
2026-09-27 (SECURITY.md Round 12): production held 17 policies that existed in no
migration, so any C-4b estimate taken from `pg_policies` before that date was counting
objects the repo could not rebuild. Migration 042 closed the gap — a rebuild and
production now hold the same 80 policies with identical predicates, recorded in
`scripts/sql/rls_policy_inventory.txt`. Re-run `scripts/sql/rls_drift_check.sql` before
sizing anything, and again after each C-4b table lands.

**C-4b needs two session variables, not one.** `current_setting('app.school_id', true)`
cannot serve a per-user predicate, and four policies have one:
`notifications_user` and `"Users can read own notifications"` are keyed on `auth.uid()`
*instead of* `auth.jwt()` (the second is gone as of 042), while `users_tenant_isolation`
(`... OR id = auth.uid()`) and `parent_students_tenant_isolation`
(`parent_id = auth.uid() AND ...`) use both. So `withTenant()` sets the tenant **and**
the acting user id, together, in the same transaction — and both inherit the staleness
trap described above, not just the tenant one.

The trap: policies read the tenant from the connection via
`current_setting('app.school_id', true)`, set with `SET LOCAL`, which is
**transaction-scoped**. The pool hands out a connection per query, so a request that sets
it outside an explicit transaction leaves it set for whoever gets that connection next.

- Fail closed on **absent**: `school_id = current_setting('app.school_id', true)::uuid`
  yields NULL when unset, which filters every row, and `WITH CHECK` errors on write.
- Fail closed on absent is **not enough**, because the failure that will actually happen
  is a **stale** value — present, well-formed, and belonging to the previous request.
  The only structural defence is that the setting is never set outside a transaction:
  no `pool.query` against a tenant table anywhere, only `withTenant()`. Enforce it with
  a route-inventory test **and** a lint rule on call sites, so a missing wrapper fails at
  review rather than in production.
- Decide this before the first policy is written. Retrofitting it across ~152 call sites
  afterwards is a different project.

**C-4b is the first failure in this whole set that no log line will announce.** A stale
`app.school_id` returns data that is well-formed, plausible, and belonging to another
school — nothing errors, nothing warns. Written rules cannot catch it; only a test that
forces the condition can. The cheap deterministic version:

- Run the suite with `PG_POOL_MAX=1`, so the same physical connection is guaranteed to
  be reused between requests. Issue a request for tenant A, then one for tenant B on the
  same pool, and assert B sees only B's rows. With one connection the leak is not
  probabilistic — it either happens every time or cannot happen.
- Assert inside `withTenant()` that `current_setting('app.school_id', true)` is empty at
  checkout. A non-empty value means the previous transaction leaked, and that is an
  error worth raising rather than overwriting silently.
- Both belong in CI, because the window where this is reachable opens the moment the
  first `app_bypass_*` policy is replaced.

> **`PG_POOL_MAX=1` in CI is not a performance shortcut. Do not raise it.**
>
> The three checks divide the problem: `PG_POOL_MAX=1` proves `withTenant()` behaves
> correctly on the paths a test walks; the route-inventory test proves the wrapper is
> used where anyone thought to look; and the checkout assertion catches the call sites
> nobody inventoried — a route that bypasses the wrapper and sets the variable on a bare
> `pool.query` leaves it set, so the *next* wrapped request on that connection raises.
>
> A pool of one is what makes that third check load-bearing. With a larger pool the
> "next request" lands on the leaked connection only by chance, and the assertion
> degrades from a detector into an opportunistic canary that passes CI and fails in
> production. The single connection is what makes "next" a guarantee.

### Smaller, for the C-4a window

`pg_tls_ca_expiring` only evaluates at boot, so it depends on deploy cadence: a quiet
period spanning the 90-day window means nobody is told. `client.ts` is being opened for
the three connection strings anyway — have the existing cron infrastructure
(`runExclusive`, Africa/Lagos) re-check `inspectCa` daily and log through the same line,
so the mechanism stops depending on how often the service happens to restart.

### ✅ CLOSED — a new user's support code could collide, failing the insert (found 1 Oct 2026, fixed by migration 050)

- a batch of m new users adds roughly m² / 1,800,000;
- with 307 users in production (measured 1 Oct 2026), a 1,600-account bulk onboarding of the size
  Child Prime's could be has about an 85% chance that at least one user insert fails.

test, a few percent per full run. Railway's wait-for-CI gate correctly skipped the deploy.

name did.

**Fixed by migration 050:** the DEFAULT is gone, and a BEFORE INSERT trigger assigns a random
six-digit code that no user holds, retrying until it finds one. `supportCode.db.test.ts` forces the

### ✅ CLOSED — the DB-suite flake was `beforeEach(seed)` hitting Jest's 5s hook timeout

The first `npm run test:db` run after migration 042 reported **1 test failing out of
166**. The run's output was read with `tail`, so the `FAIL` line naming the suite scrolled
past uncaptured, and the run was not preserved. Seven subsequent full runs — five that
day, two while landing the kobo contract — were clean at 16 suites / 166 then 171 tests.

What is known: it is not `rlsPolicyDrift.db.test.ts` (that suite was run in isolation
before and after, pass and deliberate-fail, and its assertions read only schema, which no
other suite mutates). It is not a cross-database mistake either — `src/__db_tests__/env.ts`
rebinds `DATABASE_URL` to `TEST_DATABASE_URL` before any module loads, verified while
chasing this.

**Found 28 Sep 2026, and the hypothesis above was wrong** — it is neither of the
timing-dependent suites, and it is not inside one test. `jest.db.config.js` set no
`testTimeout`, so Jest's generic 5000ms default applied to `beforeEach(seed)`, and
`seed()` TRUNCATEs every tenant table CASCADE and reinserts a two-school fixture. On a
loaded machine it exceeds 5s:

    ● adding a term › rejects an inverted date range
      thrown: "Exceeded timeout of 5000 ms for a hook.
      > 29 | beforeEach(seed);

The reason it never looked like a timeout is the second half. Jest abandons the hook when
it times out, but the in-flight INSERT keeps running and lands **after the next test's
TRUNCATE** — so the following test dies with
`duplicate key value violates unique constraint "schools_pkey"`, in a different suite,
with no timeout in sight. One slow seed takes out a variable number of later tests in a
variable place, which is precisely why it read as an unreproducible 1-in-8 event.

**How it was caught, which is the transferable part.** Not by reproducing it on demand.
The discriminator run was accidentally contaminated — it re-reads the working tree on each
iteration and ran while files were being edited, with other jest processes competing for
CPU — and that contamination is what made it fire twice in two runs. CPU contention is the
trigger, and a loaded CI machine is the same condition. A contaminated experiment that
reproduces the bug is worth more than a clean one that does not.

**The first fix was the wrong layer, and it was caught on review.** `testTimeout: 30000`
lowered the frequency and left the mechanism intact: Jest's timeout stops *waiting*, not
*work*, so the next seed to exceed 30s — a bigger fixture, a slower CI box — would
reproduce the identical cascade, and the larger number would read as a bound already
proven adequate. That is doctrine 9 applied to everything except Jest.

The real fix moved enforcement to Postgres. `seed()` is now **one transaction on one
connection** — it was ~20 separate `pool.query` calls, each its own implicit transaction,
possibly each on a different pooled connection — with `SET LOCAL statement_timeout = '20s'`
and `SET LOCAL idle_in_transaction_session_timeout = '20s'`, both below Jest's 30s. Nothing
is visible until COMMIT, and an abandoned seed cannot interleave with the next test: that
test's TRUNCATE takes ACCESS EXCLUSIVE and waits for this transaction rather than racing
it. `testTimeout: 30000` stays, as the outer backstop.

Proven by injecting a failure into the last statement of the seed and counting what was
left behind, against both versions:

| seed | schools left | users left |
|---|---|---|
| old: ~20 separate statements | **2** | **9** |
| new: one transaction | **0** | **0** |

Those 2 schools and 9 users are exactly what the next test's seed hit as
`duplicate key ... "schools_pkey"`. And `statement_timeout` demonstrably aborts rather than
being silently accepted: `SET LOCAL statement_timeout = '1s'; SELECT pg_sleep(3);` returns
`canceling statement due to statement timeout`.

One limit, stated rather than hidden: `statement_timeout` bounds each statement, not the
transaction (`transaction_timeout` is Postgres 17, and CI runs 16). A seed made slow by
twenty moderately slow statements can still exceed Jest's timeout. It no longer cascades —
the transaction guarantees that — but it will fail the run, which is correct.

*Considered and declined:* closing that limit on Postgres 16 by making the seed a single
statement — a `DO $$ … $$` block, where per-statement and per-transaction become the same
bound. It works, but it means inlining ~40 values into PL/pgSQL, losing the `user()` and
`student()` helpers every fixture edit goes through, and giving up parameterised SQL in
the one file every DB test depends on. What it buys is turning a clean failure in the
owning test into a slightly earlier clean failure in the owning test. The cascade — the
thing that actually hurt — is already closed by the transaction. Revisit if CI moves to
Postgres 17, where `SET LOCAL transaction_timeout` gives the same bound for one line.

**Load verification, done properly the second time.** Four concurrent full DB-suite runs,
**each against its own database**: 189/189 in every one, zero 5000ms timeouts, zero
duplicate keys. The first round of load verification had three of four runs sharing one
database, so they truncated each other by design; what it validly measured was only the
absence of the 5000ms-timeout signal, which is all that was claimed, but it read as more.
Sharing a database under concurrency is the invalid parallel arm described below.

**Note on the parallel arm.** The proposed in-band-vs-parallel discriminator could not be
run as stated: `seed()` truncates shared tenant tables, so concurrent suites wipe each
other's fixtures and every parallel run fails for a reason that is not the bug. The
order-preserving equivalent is `--randomize`, which is what the script used.
