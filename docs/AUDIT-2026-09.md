## Deploy runbook (production)

Do these in order. Take a Supabase backup / confirm PITR first.

1. **Measure damage (read-only).** Run `scripts/sql/audit_028_detect_overwrites.sql`
   in the Supabase SQL editor. Save all four result sets. If query 1 returns no
   rows, C-1 never happened for your data. The queries work whether or not
   migration 028 is already applied — they read `entered_by`, not the constraint.
2. **Check C-3 exposure.** From any machine:
   `curl "https://<project>.supabase.co/rest/v1/payments?select=id&limit=1" -H "apikey: <publishable key>"`
   A 200 (even `[]`) means the table was exposed until step 3.
3. **Apply migrations 028–032** (`npm run migrate` against production, or paste
   each file in order). 028 is from `main` and may already be applied — check
   `SELECT * FROM schema_migrations ORDER BY 1 DESC LIMIT 5;` first. 028 drops the
   old constraint **by name** with no `IF EXISTS`; if production's constraint
   has a different name it will fail — look it up with the first query below
   and adjust. Confirm afterwards:
   ```sql
   SELECT conname FROM pg_constraint WHERE conrelid = 'scores'::regclass AND contype = 'u';
   -- expect scores_student_subject_term_component_unique only
   SELECT class_id, subject_id, status FROM subject_result_status;  -- backfilled submissions
   SELECT relname FROM pg_class c JOIN pg_namespace n ON n.oid = c.relnamespace
   WHERE n.nspname = 'public' AND relkind = 'r' AND NOT relrowsecurity;  -- expect 0 rows
   ```
   Re-run the curl from step 2: it must now fail or return nothing.
4. **Deploy API, then web** (Railway). The API must not deploy before step 3 —
   it reads `subject_result_status` (030) on every score write.
5. **Remove** `NEXT_PUBLIC_SUPABASE_URL` and `NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY`
   from the web service. Confirm `REDIS_URL` is set on the API.
6. **Repair (only if step 1 found rows).** Run `scripts/sql/audit_028_repair_template.sql`
   as-is (it ends in ROLLBACK), review both result sets, then change the last
   line to COMMIT and run again. Send each teacher the "re-enter" list.
7. **Tell teachers**: a subject submission now locks only that subject; the
   principal can return a single subject with a reason.
8. **CI**: in Railway → service → Settings → Source, keep "Wait for CI checks"
   on; the new *Database & Isolation Tests* job now gates deploys too.

## Half-built features (found 26 Sep 2026, while deriving the C-4a privilege split)

Two tables have a read path and no write path anywhere in the API. Both are surfaced to
users, so each renders as a permanently empty feature rather than an absent one.

| Table | State | Where it surfaces |
|---|---|---|
| `principal_remarks` | read at `queries/reportCards.ts:109`; **no INSERT/UPDATE anywhere** | The report card renders `principalRemark?.remark_text`. So the document parents keep has a principal's-remark field nobody can fill — beside a form-teacher comment field that works (`class_teacher_comments` does have an INSERT). |
| `notices` | read by `getNoticesForClass`; **no INSERT/UPDATE anywhere** | Served at `GET /:schoolId/student/notices`. Students have a notice board nothing can post to. |

All three comment tables hold 0 rows in production, which is consistent with both being
unfinished rather than broken.

**For the C-4a privilege work: grant these the same as every other table.** Modelling
them as read-only would bake this accident into the privilege boundary, and whoever
later builds the principal-remark write path would get `permission denied` for a reason
nobody would connect to that change. The boundary is operation-level — no `TRUNCATE`
anywhere, no `DELETE`/`UPDATE` on `audit_logs`, no DDL — which needs no table inventory
and is the other reason to prefer it.
